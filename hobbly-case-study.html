Hobbly — Transaction State Machine & Services Platform

A high-integrity transaction engine governing multi-party reservations, idempotent payment captures, and automated dispute arbitration to safeguard unit contribution economics in service marketplaces.

1. Executive Summary & Mission

In two-sided service and booking marketplaces, a transaction is not merely a payment event; it is an extended, asynchronous operational agreement. A reservation is only complete when inventory capacity, customer pre-authorization, merchant fulfillment, cancellation windows, and payment settlement are in strict mathematical agreement. When marketplaces neglect exception handling, edge-case failures erode operating profitability.

Hobbly is an open-source transaction state machine prototype authored by Igor Grybek to enforce transactional rigor in asynchronous commerce workflows. Grounded in corporate banking cash-monitoring controls and SGH financial systems modeling, Hobbly operates under the defining principle: exceptions determine the operating model. Implemented as a deterministic Python/SQLite finite state machine (73 LOC), Hobbly models atomic booking holds, SHA-256 idempotency key deduplication, and automated ledger reconciliation across cancellations and refunds under synthetic unit-economics constraints.

2. Strategic Industry Problem & Context

Many booking and activity platforms demonstrate impressive Gross Merchandise Value (GMV) growth while suffering severe operating cash burn. The source of this economic leakage stems from three operational vulnerabilities:

  • Inventory Race Conditions: Concurrent users attempting to book the final open slot simultaneously cause double-booking errors, resulting in emergency cancellations and damaged customer trust.
  • Duplicate Payment Traversal: Network dropouts during payment handshakes cause users to retry clicks, triggering double-charging and expensive chargeback dispute fees.
  • Support Overhead Inflation: Unhandled edge cases (e.g., weather cancellations, partial host cancellations) require manual customer service intervention, easily turning a €2.00 platform take-rate into a €5.00 customer service loss.

3. System Architecture & State Machine Mechanics

Hobbly isolates transaction states, payment tokens, and operational workflows into four modular layers:

Layer Component System Mechanism Operational Function
Layer 1 Inventory Reservation Core Atomic slot locks & capacity decrementation Prevents overselling under high concurrency; holds slots during payment windows.
Layer 2 Payment State Machine (FSM) Deterministic Finite State Automaton with explicit transition guards Controls strict progression from pre-authorization to capture or cancellation.
Layer 3 Idempotency & Replay Filter Cryptographic SHA-256 request fingerprinting Guarantees that re-sent client requests return the identical result without re-charging.
Layer 4 Reconciliation & Escrow Ledger Dual-entry transaction ledger (Capture vs. Refund vs. Payout) Maintains real-time balance integrity; automates dispute disbursements.

4. 5-Dimensional Multidimensional Model

Hobbly embodies the 5-Dimensional Multidimensional Operating Model:

  • Technical Model: Python-based finite state engine with SQLite transaction persistence, atomic database transactions, and strict separation between business state and payment gateway responses.
  • Product & Operating Workflow: Enforces an explicit multi-party RACI model:
    1. Activity Organizer: Publishes listing parameters, verifies capacity, and confirms service delivery.
    2. End Customer: Holds inventory, initiates payment, and manages self-service cancellations within policy rules.
    3. Platform Operations / Support: Audits exception queues, reconciles gateway mismatches, and arbitrates complex disputes.
    4. Finance Manager: Authorizes merchant batch disbursements and monitors net contribution margins.
  • Financial Model: Detailed unit economics modeling take-rate capture, payment processor gateway fees, fraud allocations, and support handling costs.
  • Risk & Governance Model: Architectural alignment with payments standards:
    • PCI-DSS Tokenization Principles: Demonstrating architectural isolation of booking state from tokenized payment gateways.
    • PSD2 / SCA Principles: Modeling idempotency and audit controls that align with Strong Customer Authentication directives and statutory refund windows.
  • Scaling Roadmap: Conceptual architecture designed for distributed lock management and multi-currency escrow milestone disbursements.

5. Deterministic Transaction State Table

The state machine defines clear, deterministic transitions across the full reservation lifecycle:

Triggering Event Pre-Condition State Target Resulting State Operational Consequence
Reserve Slot Listing published; Capacity > 0 PENDING_PAYMENT Capacity decremented; temporary reservation lock applied.
Payment Capture PENDING_PAYMENT + Valid Idempotency Key CONFIRMED Funds captured to escrow; booking voucher issued.
Payment Decline PENDING_PAYMENT PAYMENT_FAILED Slot held during retry window before automated release.
Customer Cancel CONFIRMED (Within Policy Window) CANCELLED Capacity returned to pool; automated refund queued.
Execute Refund CANCELLED + Prior Capture REFUNDED Full captured amount returned; ledger balanced to zero net flow.
Replay Request Any State + Identical Request Key Unchanged Current State Returns cached response; prevents duplicate charge or duplicate refund.
Conflicting Key Different Booking + Existing Key REJECTED_CONFLICT Halts processing; triggers fraud inspection log.

7. Empirical Verification & Benchmark Suite

The platform is verified via 8 automated regression test suites in the public GitHub repository (hobbly-booking-payments):

  • Zero-Leakage Reconciliation: Rigorous validation showing that a €50.00 capture followed by a €50.00 cancellation refund balances to exactly €0.00 net payment flow across all internal accounts.
  • Idempotency Conformance: Verifies that identical payment keys never trigger duplicate debit transactions or duplicate refunds.
  • Cross-Booking Collision Rejection: Demonstrates that attempting to reuse an idempotency key across differing bookings is rejected with an explicit security fault.

8. Compliance, Scalability & Roadmap

Hobbly provides a modular template for scalable service commerce. Key architectural extensions include:

  1. Split-Payment Multi-Party Settlement: Automated splitting of gross booking values between organizer payout, platform commission, and statutory VAT withholding at the gateway level.
  2. Dynamic Cancellation Curve: Progressive refund schedules (e.g., 100% refund > 48h, 50% refund > 24h, 0% refund < 24h) enforced via smart contract state logic.
  3. High-Concurrency Distributed Lock: Upgrading SQLite row locks to Redis Redlock algorithms to handle flash-sale ticketing traffic spikes.
